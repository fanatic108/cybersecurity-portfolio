Windows AppLocker & Code-Signing Certificate Investigation

Investigation of a Windows application that was blocked by AppLocker after a software update. The analysis focused on Authenticode digital signatures, X.509 certificates, PKI trust chains and AppLocker publisher rules.

Scenario

A previous version of a remote-support application executed successfully, while a newly released version was blocked.

I compared the working and blocked executables to determine why Windows could no longer validate the new application as an authorised publisher.

Tools & Technologies

Kali Linux OpenSSL osslsigncode Windows PowerShell AppLocker X.509 PKI Authenticode

Investigation

I analysed the AppLocker policy, Windows Trusted Root Certificate Store and the digital signatures embedded in both application versions.

The working executable contained the expected certificate chain:

UmagDev RootCA (OU=Security)
        ↓
UmagDev IntermediateCA (OU=Security)
        ↓
UmagDev CodeSigningCert
        ↓
remote_v1.exe

The new executable contained the code-signing certificate but did not contain the required intermediate CA certificate. 

remote_v2.exe
CodeSigningCert
Issuer:
OU=Sec
CN=UmagDev IntermediateCA

Key Findings

  • The Windows AppLocker executable policy was enabled and used a publisher-based allow rule for UmagDev.
  • The UmagDev Root CA was present in the Windows Trusted Root Certification Authorities store.
  • The working executable included the required intermediate certificate.
  • The new executable did not include the required intermediate CA certificate.
  • A certificate issuer difference was identified: OU=Security in the working chain versus OU=Sec in the new signing certificate.

Root Cause

The certificate chain for the new executable could not be successfully constructed to the trusted UmagDev Root CA.

Because the publisher could not be validated through the expected certificate chain, the executable did not satisfy the enforced AppLocker publisher rule and was blocked.

Security Recommendations

  1. Include the correct intermediate CA certificate in the Authenticode signature and verify the complete certificate chain before software distribution.
  2. Implement automated release validation to verify digital signatures, certificate chains, issuer information and trust before publishing software.
